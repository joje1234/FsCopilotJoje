# Shared vanilla definitions

The EFB shared-flight catalog currently contains only the Black Square Baron
58P (`bksq-aircraft-baronpropress`). The compiler/runtime accept other profile
identities; this does not make all vanilla YAML aircraft EFB-ready. Each needs
its complete include tree, control-role map, cockpit policy and simulator
verification. Review group applicability for other engine/avionics types and
keep aircraft differences in data rather than runtime name branches.

Cockpit policies may opt into `sharedAutopilot: true` for normal bidirectional
AP mode/selector sharing; the default is false. Navigation/screen events and
physical controls stay separate. An optional `tolerances` dictionary declares
finite readback precision per entry (0 < value <= 1); the default is 0.000001.
Heading uses 0.022 degrees for SDK event quantization. This does not change
hardware alignment tolerance or assign barometers to an AP/seat owner.

Elevator, aileron and rudder trim use ordinary bidirectional instrument sync,
independent of Steering ownership. Their definition setters use absolute SDK
events with precision declared in the cockpit policy. They are excluded from
physical control roles, learning, pickup and parked output checks. Wire axis
slots 6..8 remain reserved so existing engine indices do not change. Ordinary
cockpit protocol v2 acknowledges individual peer adjustments, preventing an
older host receipt from rolling back a newer local turn; both helpers must match.

This library builds the existing `FsCopilot/Simulation/Definitions.cs` loader
and expression engine for the desktop app, EFB helper and tests. Aircraft
variables/setters stay in the ordinary vanilla YAML files.

`Definitions/controls/<aircraft-directory>.json` selects the existing entries
used for each engine control role and declares their normalized range. It does
not specify another setter. Selection rejects missing/ambiguous entries,
partial engine groups, unsupported expressions and toggle/relative setters.
Rudder and both brakes now select standard absolute definitions too. The generic
`modules/flight_controls.yaml` rudder route matches vanilla `apply_surfaces`' sign;
brakes reuse the aircraft's existing EX1/Position 32k setters. The compiler
executes and validates simple absolute affine setters (offset or sign), recording
separate read and output domains. It does not execute arbitrary RPN in WASM.
Roll/pitch retain their working learned fallback. Tiller uses the definition's
absolute AXIS_STEERING_SET event, with conversion before SDK argument rounding.
Its event sign is opposite to STEER INPUT CONTROL, confirmed by actual MSFS
readback in 0.9.7. The negative scale stays in the shared YAML definition.

The helper automatically selects the aircraft directory from native observations,
loads its vanilla tree/role map and compares the computed adapter fingerprint
and engine count with the native module before permitting session setup. Each
selection is immutable until the native instance or aircraft changes.

Supported scalar domains are currently 0..100 Percent, 0..16384 Position 16k,
0..32768 Position 32k, signed rudder -16384..16384, and 0..1 Number/Percent Over 100. Mismatched domains are rejected before a check
can mistake a rescaled write for the original cockpit position.

The native module uses a catalog generated by `FsCopilot.Definitions.Compiler`
from those same definitions. Direct AVar output uses the SDK, LVars use native
explicit-unit lookup/get/set, and absolute K setters use the masked event route.
The existing native writer still enforces session, owner, generation, sequence
and confirmed hardware-mask checks before any output.

Currently the catalog is generated **at build time**. Changing physical control
roles/setters requires rebuilding the matching Community package and helper.
Runtime profile upload is not implemented. Missing profiles are unavailable for
shared controls; the catalog currently contains the validated target aircraft's
ten roles (six engine, rudder, tiller and left/right brake). This is a generic execution mechanism, not a claim that every
downloaded aircraft profile has been validated.

`FsCopilot.Efb/build.ps1` runs the compiler before building WASM. The standalone
EFB therefore retains its cockpit references without requiring the helper for
local Me/Mock testing. Saved hardware mappings keep their existing aircraft key
and on-disk format.

Remote-control support requires parked checks for Steering, Throttle, RPM and
Mixture. Setup wizard handles masking, small bounded output probes, readback
and restoration. Compatible results and hardware mappings are saved between
sessions; relevant definition/calibration changes invalidate affected checks.
Reset setup clears this aircraft's learning/checks on explicit confirmation,
without restarting MSFS. No check moves controls automatically at startup or
on helper discovery.
